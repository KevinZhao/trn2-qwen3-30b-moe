vllm-neuron 多序列打包 prefill：改造思路

Qwen3-30B-A3B · 单 Trn2 device，TP4 / LNC2 · vLLM 0.29 / vllm-neuron 0.29 · 2026-11-09

一句话：把多条新请求的 prompt 首尾相接，拼成一条长序列，用一个已编译好的 prefill 图一次算完；attention 用块对角的 causal mask，保证各条序列互相看不见。
收益：ShareGPT c16 的 TTFT P99 从 1141 降到 276 ms，c32 从 2405 降到 581 ms；TPOT 也降了 9–15%；GSM8K 不变（0.946）。

1. 要解决的问题

  • vllm-neuron 0.29 调度器写死了 max_prefills_per_batch = 1（scheduler.py:285），一个 step 只能跑一条 prefill。
  • 短 prompt 的 prefill 受权重带宽限制：每个 step 有约 60 ms 固定开销（每次都要读全部 128 个专家），之后每个 token 只多约 0.04 ms。
  • 16 条请求同时到达时，TTFT 呈阶梯状，每级 75–90 ms，P99 约 1.3 s（NJ 基线实测）：
req#1 65 ms ▏
req#2 128 ms ▏▏
req#3 199 ms ▏▏▏
…
req#16 1311 ms ▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏▏

打包的本质是把 16 次固定开销合成 1–2 次。H100 上的 vLLM 本来就会把这 16 条放进同一个 8192-token 的 step。

2. 为什么改动量不大

不能简单地把 max_prefills_per_batch 调大，会同时撞上 5 个问题： (a) 每条请求各自补 bucket，总长不是已编译的形状； (b) 请求数那一维没有编译过； (c) segmented attention 只认 block_tables[0]，会跨序列做 attention； (d) MoE 的 padding mask 会静默置零； (e) 超出 budget 的最后一条会被切成 chunk。

但仔细读代码后发现，大部分基础已经具备：

runner 输入构建

继承自 GPU vLLM，本来就是多请求写法：cu_num_tokens、逐 token 的 slot_mapping、逐请求的 logits_indices。KV 按 slot scatter 写入，不用改。

attention

不用自己写 kernel：nkilib attention_cte 自带 sequence packing，用 bound_min/bound_max 指定每个 query 能看到的 KV 区间，可以和 causal 同时生效（qwen3_vl 视觉编码器在生产里用）。

sampling

on-device 贪心采样本来就按行处理，一次输出 K 行没有障碍。

真正写死「只有一条」的只有 4 处：调度器准入、调度器补 bucket、prefill 图里请求数那一维的形状、attention。

3. 打包后的数据长什么样

示例：4 条请求打包进一个 T = 1024 的 bucket，padding 全部挂在最后一条上。

r0
req1 · 210
req2 · 500
req3 · 120
padding 157（算作 req3 的一部分）
37 + 210 + 500 + 120 = 867 个真实 token，补到 1024。positions 每条序列都从 0 开始，RoPE 自然正确。

块对角 causal mask（示意，每格代表一段 token）

每个 query token t 只看 [bound_min[t], t] 区间内的 KV：
  • bound_min[t]：t 所属序列在缓冲里的起点
  • bound_max[t]：该序列的终点（padding 算作最后一条序列的一部分）
  • 上三角部分由静态 causal 跳过；跨序列的下三角 tile 照样会计算，只是被动态 mask 屏蔽掉

4. 四层改动

① 调度器决定谁能一起打包、总长补一次
→
② runner把形状固定成已编译的样子，生成 bound / valid
→
③ worker编译和 warmup 打包图
→
④ 模型attention 传 bound，MoE 用显式 mask

① 调度器 vllm/core/scheduler.py

改动点内容
准入条件只打包「干净」的请求：新请求、整条 prompt 能放进 budget、前缀缓存命中为 0、没有结构化输出 / 多模态 / KV-transfer。不满足的照旧走单条路径。
累计规则按 FCFS 往后累计，直到 pack_max 条或总长达到 pack_budget；遇到第一条不满足条件的就停，不插队。
容量计数max_num_seqs 和 KV 并发上限都要把 waiting 里的请求算上，否则一次放进 K 条可能超限。
补 bucket原来每条请求各自补到 bucket（3 × 100 token 会变成 128 × 3 = 384，这个形状没编译过）。打包 step 改成总长只补一次，补到打包 bucket，padding 全挂在最后一条上。
与 P4 旋钮的关系一个打包 step 算作「一次 prefill」，之后照样插 dsbp 个 decode step。

② runner vllm/worker/neuron_model_runner.py

改动点内容
请求数维度block_table、sampling_positions、sampling_params 的行数固定为 K = max_num_seqs，不足的行补齐，像 decode padding 一样被忽略。
attention 分支强制走 full 分支（kv_segment_size=0）。segmented kernel 只有一个全局的 prior_tokens，表达不了多条序列。
新增张量pack_bound_min、pack_bound_max、pack_valid，都是 [T]，放在设备上。
max_query_len传 T，不传每条请求的最大长度。dynamo 会对这个 Python int 做值 guard，每出现一个新值就会触发运行时编译（分钟级卡顿）。
warmup / trace用 kv_segment_size = -1 作为哨兵，表示「打包变体」。

③ worker vllm/worker/neuron_worker.py

对每个打包 bucket 编译一个打包图。坑：_warmup_prefill 自己写了一套 bucket × kv 循环，没有复用编译目标列表，要单独加一个打包循环。

④ 模型 model_bf16.py（两处，合计约 30 行）

  • full 分支调用 flash_attention 时传入 bound：expand 成 [头数, T, 1] 并做 contiguous（kernel 按连续布局做 DMA）。
  • MoE 的 padding mask 必须改，见下面的红框。
最大的坑：静默出错。原代码用 arange <= argmax(positions) 推断最后一个真实 token。打包后 positions 是锯齿形的，argmax 只会指向第一条最长序列的末尾，其它序列的 token 都会被判成 padding，MoE 输出被置零。不报错，只给错答案。改成直接用 pack_valid。边界用例里一定要有「多条序列等长」的情况。

5. 编译策略：让 NEFF 数量尽量少

决策理由
请求数那一维不分 bucket，固定为 max_num_seqs每个 rank 读一遍 lm_head 权重约 0.2 ms，和行数无关，多算几行可以忽略。这样每个打包 T bucket 只多 1 个 NEFF；如果请求数也分 {4, 8, 16} 三档，NEFF 数会翻 3 倍，没有收益。
打包 bucket = 512 / 1024 / 2048 / 4096128 一次只能装 1–2 条，收益太小；8192 会让所有请求一起等约 400 ms，ITL 也会被拉长（实测见第 8 节的 RS8）。
K = 1 走原来的 segmented NEFF原有路径完全不受影响；单请求 TTFT 扫描实测与不打包时相同。

6. 开关与回滚

开关作用
P5_PACK=1总开关。关掉时行为和补丁前完全一样。
knob 文件里的 pack_max / pack_budget运行时可调，不用重启；pack_max=1 就是关闭。
P5_PACK_BUCKETS打包 bucket 列表，默认 512,1024,2048,4096。
实现方式scripts/p5_patch_pack.py 对 site-packages 做带计数断言的字符串替换（每处替换都断言命中次数），原文件有备份，每次都从备份重新打补丁。

7. 正确性怎么验证

检查项方法与结果
首 token直接来自打包 prefill 的 logits：16/16 一致。
贪心续写完全一致率要和「batch 组成噪声」比，不能要求 100%。不打包时，逐条发和 c16 同时发相比也只有 12/16 一致（bf16 下不同 T 的 kernel 数值不同）；打包后是 11–13/16，处在同一水平。
边界用例多条等长序列（专门测 argmax 的坑）、极短 prompt、总长恰好等于 bucket、满载 K 条、混入前缀命中的请求（应该回退到单条）。
端到端GSM8K 500 题 0.946，和不打包相同；RS4（51 min，5587 请求）、RS7（51 min，6089 请求）两次 soak 都是 0 失败。
确认生效steplog 里要看到多请求的 prefill step。
踩过的坑：第一次上机时，编译通过、NaN 检查也 PASS，但打包从来没有生效。原因是 vLLM 0.29 的 find_longest_cache_hit 返回 3 元组，补丁按 2 元组解包，前缀命中探测抛异常后，代码保守地关闭了打包，只留了一行日志。修复只改调度器的 Python 代码，不需要重编译。经验：新功能要有一个「确实生效了」的正向指标，不能只看没有报错。

9. 局限

  • 中位数略有上升：同一个打包 step 里最短的请求要等最长的请求一起算完。
  • 长 prompt 仍然串行：总长超过 pack_budget（4096）就不打包；random 3000 token 以上的负载和不打包相同（±1–2%）。
  • 跨序列的计算浪费：跨序列的下三角 tile 照样会计算，计算量约等于对整个 T 做 causal。设计阶段估计额外开销 0–10 ms，没有单独测过。
  • 功能限制：只支持 all_greedy，不支持结构化输出、投机解码、多模态；前缀命中的请求不打包。
  • 工程形态：目前是对 vllm-neuron 0.29 的字符串替换补丁，要贡献上游就得重写成正式代码，并把 pack_bound_* / pack_valid 定成各模型通用的接口。

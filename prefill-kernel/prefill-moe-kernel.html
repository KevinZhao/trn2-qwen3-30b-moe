1. 先弄清楚：Prefill 时 MoE 层在做什么

Qwen3-30B-A3B 每层有 128 个专家（每个专家是一个小 MLP），每个 token 由 router 挑选其中 8 个。一次 prefill 会同时处理一整段输入（几百到几千个 token），于是每层 MoE 要做三件事：

  1. 分组（mapping）：根据路由结果，把 token 按专家归类——“哪些 token 要去专家 5？”
  2. 专家计算：每个专家拿到属于自己的 token，做 gate_up 矩阵乘 → SiLU 激活 → down 矩阵乘。
  3. 合并（combine）：每个 token 把 8 个专家的结果按路由权重加起来。

Neuron 上的计算图必须在编译时确定形状和循环次数（运行时不能“看情况多跑几次”），所以官方实现把每个专家的 token 切成固定大小的块（block，128 个 token 一块），并按最坏情况预留块数——真实用不满的块就是“空块”。下面的动画用简化尺寸（4 个 token 一块、6 个专家）演示这个过程：

2. 三分钟了解 Trainium2 的“厨房”

要理解为什么慢，需要知道 Neuron 芯片和 GPU 最大的不同：数据搬运是显式的。

计算引擎（每个 NeuronCore 里）

  • PE（Tensor Engine）：128×128 的矩阵乘阵列，干重活的“主厨”。
  • ACT（Scalar Engine）：激活函数（SiLU 等）、逐元素运算。
  • DVE（Vector Engine）：向量运算、数据拷贝。
  • GpSimd（Pool）：通用小核，什么都能干但不快；软件 DGE 就是靠它生成 DMA 描述符。

这些引擎各自独立执行自己的指令流，彼此通过信号量同步——相当于厨房里各管一摊的几个人。

存储层次

  • HBM（芯片 96 GB）：放权重和 KV cache，容量大但远——相当于“冷库”。
  • SBUF（每核约 24 MiB 片上内存）：计算只能读这里——相当于“操作台”。
  • PSUM：矩阵乘的累加缓冲区。

关键：没有 GPU 那样的自动缓存。HBM → SBUF 的每一次搬运都要由 kernel 明确发起一条 DMA；搬什么、什么时候搬、搬完放哪，全靠程序安排。

DMA 描述符与两种 DGE：本次优化的关键背景

DMA 引擎搬数据需要“描述符”（从哪个地址搬多少字节到哪里）。如果地址在编译时就知道，描述符可以提前生成；但 MoE 的地址取决于运行时的路由结果（“这一块是第几号专家”“这一行是第几个 token”），必须在运行时现生成。Neuron 有两种做法：

软件 DGE（software DGE）硬件 DGE（hardware DGE）
谁生成描述符GpSimd 引擎用软件逐条算出来DMA 硬件根据一条指令自己展开
能力最灵活：每一行都可以是不同地址（逐行 gather）适合“一个动态基地址 + 固定形状”的整块搬运
代价描述符由 GpSimd 现算。大块连续搬运时也能接近带宽上限（实测约 348 GB/s/核）；但描述符细碎时 GpSimd 生成跟不上，原版 MoE 实测只有约 135 GB/s，且 GpSimd 71% 时间忙于生成描述符不占 GpSimd，指令由 Sync/ACT 等引擎的队列发出；与软件 DGE 是两条独立通道，可以并行
类比一个服务员手写每张取货单传送带：给个起点，自动成批运货

本次的核心洞察之一：专家权重是整块连续的（只需要“专家号”一个动态偏移），完全可以交给硬件 DGE；只有按 token 逐行 gather 才真正需要软件 DGE。官方实现把两者都放在了软件 DGE 上。

如果你熟悉 GPU：为什么同样的写法在 GPU 上不太会这么慢？

GPU 有 L2 cache 和成千上万个线程，硬件会自动把“等内存”的线程换下去、让别的线程算，从而掩盖访存延迟；重复读同一份专家权重时，cache 也能帮上忙。Neuron 的做法是把调度交给编译器和 kernel：没有自动缓存，也没有线程切换来掩盖延迟，搬运和计算的重叠必须写在程序里。所以一个“每块都重新搬一遍权重、所有搬运挤在一条慢队列上”的 kernel，在 Neuron 上会被直接暴露成瓶颈。

3. 改进前：官方 moe_cte 是怎么做的，慢在哪里

官方实现按块处理：每一块都把这个专家的权重（TP4 切分后每份约 2.25 MB）从 HBM 搬进 SBUF，再 gather 这一块的 128 个 token，算完写回结果。我们用 neuron-explorer 在 T=2048（一次 prefill 2048 个 token）下逐层 profile，得到：

问题实测现象（T=2048，每个物理核）
① 权重不复用每块都重新搬一次专家权重 2.25 MB，即使相邻两块是同一个专家；加上 token gather 与输出读改写，每块约 3.4 MB
② 所有搬运挤在一条软件 DGE 队列98% 的 DMA 字节（364 MB 中的 334 MB）走 GpSimd 软件 DGE，实测约 135 GB/s；GpSimd 有 71% 的时间在生成描述符
③ 空块照样执行按最坏情况预留 191 块，真实只有约 145 块；空块同样要走完整流程
④ 分组本身很重mapping 用到 indexed_flatten 和 TP 集合通信，每层约 0.33 ms
结果每块约 3.4 MB ÷ 135 GB/s ≈ 25 µs 搬运，实测每块约 28 µs，而理想矩阵计算只要约 7 µs；PE 大部分时间在等数据

4. 改进后：新 kernel 的五个改动

一句话：按专家顺序排好队，每个专家的权重只搬一次；权重走硬件 DGE、token 走软件 DGE，两条队列并行；搬运提前发起，和计算重叠；空块不搬数据。先看整体效果——下面两条时间线用同一个时间轴，同时开始：

搬专家权重 gather token / 写结果 PE 矩阵计算 空块

示意动画：12 个块（9 块真实 + 3 块空块），专家序列 E5 E5 E9 E14 E14 E21 E21 E21 E30。时长按实测量级设定：改进前每块权重 2.25 MB + token/输出 1.15 MB，按 135 GB/s 计；改进后 PE 每项 8.3 µs（T=2048 实测平均），硬件 DGE 搬权重的时长为示意值。真实 T=2048 每核约 96–128 块。动画里 PE 只画了理想的矩阵计算时间；实测原版 PE 约 60% 的时间有指令在执行（含转置、拷贝等辅助指令，以及功耗节流拉长的时间），但同样是在等搬运。

改动 ①：按 lane 切分，专家变了才重新搬权重

分组后，所有真实块按专家编号顺序排成一列（同一个专家的块挨在一起）。新 kernel 把这一列切成 8 段连续的 lane（2 个物理核 × 每核 4 条 lane），每条 lane 在 SBUF 里有一块自己的权重缓冲区。PE 轮流处理各 lane 的下一块；只有当某条 lane 的下一块换了专家时，才重新搬权重。

示意：一个核的 4 条 lane、共 24 个块（这里假设平均每个专家 2–3 块，对应较长的 prefill）。T 越大，每个专家分到的块越多，复用越明显；T=2048 时平均每个专家约 1 块，此时主要收益来自改动 ② ③ ④。

改动 ②：权重改走硬件 DGE，与 token gather 分两条队列

权重搬运是“一个动态基地址（专家号）+ 固定形状”的整块拷贝，交给 Sync 引擎队列上的硬件 DGE：不占 GpSimd，也不和 token gather 抢同一条队列。token gather（每行一个不同的 token 地址）留在软件 DGE 上。两条队列并行后，搬运不再是单车道。

更准确地说：软件 DGE 本身不是慢在“软件”两个字上——大块连续搬运时它也能接近 HBM 带宽（后续大型 MoE 实验实测约 348 GB/s/核，三种方式相同）。原版慢在“每块重搬整个专家 + 搬运被拆成大量细碎描述符、全靠 GpSimd 现算”。所以真正起作用的是“少搬”（复用）和“别让 GpSimd 成为瓶颈”（权重换到硬件通道），而不是硬件 DGE 天生更快。

改动 ③：空块跳过所有数据搬运

循环次数仍然必须是编译期常量（预留上界不变），但空块的 token 下标是 −1，新 kernel 对这些项的所有 DMA 使用越界跳过（oob skip），一个字节都不搬。注意：空块仍会占用一些 PE 时间（这是剩余的优化空间之一）。

改动 ④：静态展开 + 跨块软件流水，让 PE 不等自己

每个块在 PE 上分 4 个阶段：S1 把 token 转置（PE）→ S2 gate_up 矩阵乘（PE）+ SiLU（ACT/DVE）→ S3 中间结果转置（PE）→ S4 down 矩阵乘（PE）+ 写回。每个 PE 阶段都要等前一步 ACT/DVE 的结果。如果按块顺序执行，PE 每块会空等两次；新 kernel 把指令顺序排成 S3(k) S2(k+1) S1(k+2) S4(k)，PE 等待的那段时间正好去做别的块的活：

PE 阶段 ACT/DVE 处理（激活、拷贝） 图中数字是块编号

示意：4 个块，阶段时长为示意值。实测旧版顺序执行时，PE 在每次 S2、S3 之后约有 2 µs 空泡。

为什么不用动态循环（运行时只跑真实块数）？我们试过 fori_loop：每次迭代进出都会清空所有 DMA 队列、让所有引擎做一次屏障同步，两个物理核的迭代次数还必须相同，否则设备会卡死。实测按专家动态循环 4.3 ms、每次迭代两路 3.3 ms，都比原版（2.7 ms）还慢。所以最终方案是“静态上界 + 空块跳过搬运 + 完全展开流水”。这个结论只针对小专家：每块只算几微秒，每次迭代几十微秒的同步开销占比太大。大型 MoE（如 DeepSeek-V3）每组计算约 0.7 ms，动态循环的开销就可以忽略，那边的实验正是按专家动态循环实现的。

改动 ⑤：mapping 与 combine 都变轻

mapping（分组）

改进前：调用 build_blockwise_mapping，内部 indexed_flatten 约 330 µs，还有 TP 集合通信。

改进后：每个 rank 自己用 find_nonzero_indices 扫一遍 128 个专家，加几个小的 torch 运算，不再需要集合通信。T=2048 时 mapping 约 0.20 ms。

combine（合并）

改进后：专家输出在 kernel 里直接写到“按 token 排列”的位置（每个 token 8 行），再由一个小 kernel 在 PE 上用 fp32 把 8 行加起来。T=2048 时约 0.16 ms。

附带好处：相对 fp32 参考的误差（rel-fro）从 4.36e-3 降到 2.87e-3。

6. 为什么说所有 MoE 模型都能受益

  • 瓶颈在共用路径上，不在 Qwen3 里。vllm-neuron 中的 MoE 模型在 prefill 时都走同一套 moe_cte → nkilib blockwise kernel。“每块重搬权重”“所有搬运挤在一条软件 DGE 队列”“空块照算”“mapping 带集合通信”这四个问题都来自 kernel 本身的结构。
  • 专家越细，越吃亏，收益也越大。现在的主流 MoE 都是“专家多、每个专家小”（Qwen3 每个专家中间维度 768，TP4 后每 rank 只有 192）。每块的计算量小、权重搬运占比大，原版就越是被搬运卡住。
  • prefill 占比越高，收益越大：长输入、RAG、Agent 多轮对话。
边界：
  1. 每块的计算/搬运比只取决于“这次搬进来的权重被多少个 token 用”（每块 128 个 token ≈ 128 FLOP/字节），和专家大小无关，所以大专家同样受益；但大专家的权重放不进 SBUF（例如 DeepSeek-V3 单个专家约 88 MB，SBUF 每核约 24 MiB），需要改成“按权重分片、每片在该专家的所有块之间复用”的循环结构。已有专用 kernel 的模型（如 PR #73 Hy3-FP8）需要单独对比。
  2. 当前实现是 Qwen3 专用版：写死 E=128、每 rank I=192、H=2048、bf16，T 须为 128 的倍数（vLLM 的 bucket 都是 2 的幂，所以实际服务中不会遇到）。推广需要参数化形状、支持 FP8 权重、支持专家并行。
  3. decode 走另一套 kernel，不受影响。
